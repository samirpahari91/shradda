HOW TO USE THIS DOCUMENT
--------------------------------------------------------------------------------
Work top to bottom. Every stage ends with a CHECK line stating exactly what you
should see. If a CHECK fails, stop and fix it before moving on -- later stages
assume earlier ones succeeded, and a silent failure here ends up as a wrong
number in a thesis table or on a public web page.

Commands are written for Windows PowerShell, which is what this project was
built on. On macOS/Linux the Python and Node commands are identical; only the
path separators and the file-inspection commands differ.

Notation:
  >    a command you type
  ->   expected result
  !!   a trap that has actually bitten this project

Total time from scratch: about 60-75 minutes, almost all of it unattended in
Stage 4 (notebook) and Stage 5 (training). Re-deploying an existing checkout
takes under 10 minutes because both CV stages are cached.

================================================================================
STAGE 0 -- WHAT THIS PROJECT IS (read once, it prevents most mistakes)
================================================================================
Two halves that must stay in agreement:

  ANALYSIS    LPBF_ML_Analysis.ipynb   -- the thesis narrative: cleaning,
              imputation, feature engineering, per-target modelling, ablations,
              benchmarks, leakage correction. GENERATED from build_notebook.py.

  DEPLOYMENT  docs\                    -- a dependency-free static web app that
              runs the selected models in the browser. Fed by docs\model.json,
              which train_export.py writes.

Three ideas you must not mix up:

  1. FLAT grouped CV       outputs\grouped_model_comparison.csv
     Ranks every candidate model per target. USE FOR: choosing a model.
     NEVER quote as a final score -- it selects and scores on the same folds,
     so it reads about 0.02-0.04 too high.

  2. NESTED grouped CV     outputs\nested_grouped_results.csv
     Inner loop selects, outer loop scores. THIS IS THE CITABLE NUMBER. It is
     what docs\model.json ships and what the web app displays.

  3. RepeatedKFold         historical, superseded
     Leaks replicate rows across train/test. Inflates Grain Size by 0.28 and
     Yield Stress by 0.23. Present in the docs only as a cautionary comparison.

!! The single most likely error in this project is quoting a flat number as a
   headline result. Stage 7 has an automated gate specifically to catch it.

Files you edit vs files you never edit:
  EDIT   build_notebook.py, train_export.py, docs\js\*, docs\css\*, docs\*.html,
         README.md, METHODOLOGY_README.md, result_explaination.txt
  NEVER  LPBF_ML_Analysis.ipynb (regenerated -- your edits are destroyed)
         docs\model.json         (regenerated by train_export.py)
         docs\test_vectors.json  (regenerated by train_export.py)
         outputs\*               (regenerated by the notebook / trainer)

STAGE 4 -- EXECUTE THE NOTEBOOK  (~25 min, unattended)
================================================================================
4.1  Preferred command, works everywhere:

  > python _run_nb.py

4.2  The documented alternative is `jupyter nbconvert --execute --inplace
     LPBF_ML_Analysis.ipynb`. Use it only if your Jupyter install is clean.

!! On this machine nbconvert FAILS BEFORE RUNNING A SINGLE CELL with
   "ModuleNotFoundError: No module named 'jupyter_contrib_nbextensions'".
   Cause: a user-level config in %USERPROFILE%\.jupyter registers that
   preprocessor globally, but the package is absent from the active env. The
   traceback names nbconvert internals and looks like a code failure -- it is
   not. _run_nb.py drives the same nbclient engine and skips that config layer.
   Permanent fix: remove the stale preprocessor entry from
   %USERPROFILE%\.jupyter\jupyter_nbconvert_config.py (or delete the file).

4.3  CHECK -- this is the authoritative verdict, not the console log:

  > python _check_nb.py
  -> 19/19 code cells with output, 0 error cells
     OK -- notebook executed cleanly
  > echo $LASTEXITCODE
  -> 0

!! During this run the console prints several joblib/loky "Traceback ...
   KeyError: ...joblib_memmapping_folder..." blocks. These are BENIGN -- the
   parallel-worker resource tracker racing on temp-folder cleanup at shutdown,
   a known Windows quirk. They are not in any notebook cell. Judge success by
   the 4.3 check (0 error cells), never by grepping the log for "Traceback".

4.4  The notebook writes figures and its own metric CSVs into outputs\. It does
     NOT write nested_grouped_results.csv or grouped_model_comparison.csv --

  > Get-ChildItem outputs\nested_grouped_results.csv, outputs\grouped_model_comparison.csv | Select-Object Name, LastWriteTime

STAGE 5 -- TRAIN, SELECT AND EXPORT THE BROWSER MODEL
================================================================================
5.1  Full run, recomputing both CV stages from scratch (~45 min):

  > python train_export.py --refit-cv

5.2  Fast run, reusing the cached CV CSVs (~1 min). Correct whenever you have
     only changed export logic, metadata or presentation -- not the data,
     features or candidate models:

  > python train_export.py

     Flags:
       --refit-cv    recompute flat + nested grouped CV (ignore the cached CSVs)
       --full-trees  export full ensembles instead of thinning to 120 trees
                     (payload grows ~4x; only for diagnostics, never for Pages)

5.3  What it does, in order: clean -> physics-impute energy densities -> add
     engineered ratios -> score every candidate per target under flat grouped CV
     -> nested grouped CV for the honest headline -> refit the winner on all
     labelled rows -> export docs\model.json -> self-verify.

5.4  CHECK -- every target must report verify=OK:

  -> Hardness (HV)          RandomForest/deep  trees=120 (of 500) verify=OK (err=4.92e-08)
     Yield Stress (MPa)     ExtraTrees         trees=120 (of 500) verify=OK (err=3.33e-07)
     ... one line per target, seven in total ...
     wrote docs/model.json  (5.04 MB)
     Done.

     The self-verify re-implements the exported JSON in Python and requires it
     to reproduce scikit-learn's / XGBoost's own predict() to within 1e-6. On
     failure the script ABORTS rather than shipping a silently wrong model.
     Trust the abort: never work around it.

5.5  Expect the deployed model per target to differ occasionally from the
     nested most_selected column. Relative Density ships XGBoost/reg while
     XGBoost/mid won most inner folds. That is EXPECTED -- the deployed model is
     the overall winner, the nested column is the per-fold favourite, and no
     selection rate reaches 100%.

7.3  Reliability tiers have ONE definition: the RELIABILITY dict in
     train_export.py, exported into model.json as a `reliability` block.
     docs\js\app.js reads it to draw the badge; _check_docs.py reads it to
     validate the README. Change a cutoff in train_export.py, re-export
     (Stage 5.2), and all three move together.

       Tier             Regression (R2)   Classification (lift over chance)
       Reliable         >= 0.60           >= 0.55
       Indicative       >= 0.45           >= 0.30
       Low confidence   below 0.45        below 0.30

     Classification uses lift = (score - chance)/(1 - chance) with
     chance = 1/n_classes, because balanced accuracy 0.5 is worthless on two
     classes and respectable on six.

!! If this gate reports "schema 2 ... using fallback", your model.json predates
   the reliability block. Re-run Stage 5.2 to export it.

   - A 404 on model.json almost always means Folder was left at "/" instead of
     "/docs". Re-check Settings -> Pages.

     underscore. docs\ currently has none, so this is fine. If you ever add

STAGE 12 -- ROUTINE MAINTENANCE RECIPES
================================================================================

  -> python _check_docs.py -> fix any README labels it flags -> commit.

  node verify_js.mjs -> Stage 8 local check -> commit. No retraining needed.

Added or changed a feature, target, or candidate model?
  python train_export.py --refit-cv   (full ~45 min; the cached CSVs are now
  invalid) -> both gates -> update the docs tables -> commit.
  The web form is generated from the `features` metadata in model.json, so a new
  input appears in the UI automatically; no JavaScript change required.

Changed the analysis narrative?
  Edit build_notebook.py -> Stage 3 -> Stage 4. Never edit the .ipynb.

Numbers look suspiciously good?
  Suspect leakage first. 129 of 674 rows share an identical process-input vector
  with another row. Confirm folds are grouped on that vector, and read
  METHODOLOGY_README.md section 7a before believing any improvement.

--------------------------------------------------------------------------------
LIMITATIONS TO RESTATE WHENEVER YOU PRESENT THIS WORK
--------------------------------------------------------------------------------
  - Screening tool, NOT a qualification tool. Predictions are alloy-agnostic
    averages across many materials, machines and powders. Expect a real offset
    for any single machine until recalibrated against your own measurements.
  - Grain Size (R2 0.352, fold s.d. +-1.709) and Yield Stress (R2 0.426, below
    the 0.45 cutoff) are Low confidence. Treat them as directional only.
  - No extrapolation. Tree ensembles clamp to their edge prediction outside the
    training envelope. The app warns; it cannot fix it.
  - Range-to-midpoint parsing discards within-range uncertainty.
  - Median imputation pulls predictions toward the corpus average when many
    fields are left blank.
  - 'Scanning strategy' was dropped (52.2% missing), so the models are blind to
    scan pattern.
  - Small per-target samples (173-447 rows) mean wide intervals. Always quote
    the +- standard deviation, never the mean alone.
